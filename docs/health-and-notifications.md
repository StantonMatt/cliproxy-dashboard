# Health and account notifications

Inside the Overview’s Codex region, below **Codex routing**, the compact health strip shows the managed Linux Codex server, gateway, configured Codex account emails, and last successful backup. Green requires recent observations. Missing/ambiguous data is unknown, old observations are stale, and failures remain visible. A bootstrap unit's active/exited status is never taken as proof the shared daemon is healthy.

On the phone, use **[http://router:8409/](http://router:8409/)** with Tailscale connected and Tailscale DNS enabled. The IP fallback is `http://100.64.0.10:8409/`. This is an allowlisted dashboard through the private proxy, restricted to your known devices. It allows data refresh, routing changes, automatic reset policy changes, and reset redemption. Raw gateway management routes remain blocked. The dashboard backend remains on Linux loopback; the Mac's `router.localhost:18320` is a separate SSH tunnel address.

- Codex is probed every 30 seconds with the installed CLI's read-only `app-server daemon version` command, as the normal user. The probe does not start a daemon, submit a model request, or load a task. After 120 seconds without a probe result, its state is stale.
- Gateway/account checks reuse the existing one-minute quota polling. Success older than 180 seconds is stale. Exhausted allowance, unavailable account, failed refresh, and sign-in required are distinct from healthy.
- A backup older than 36 hours is stale; a failed backup run does not erase the last success date. Backup storage is explicitly same-disk.
- Usage collection is checked every 30 seconds using the usage service's `Result` and `ExecMainStatus`, plus the usage timer's active state and the collector's status file. A failed last run or inactive timer is unhealthy. Success older than five minutes is stale, even when no new requests arrive. The last successful run survives collector/probe restarts; a running collection does not count as a completed success. Health observations older than 120 seconds are stale, and unavailable unit status is unknown.
- After each run holding the collector lock, the collector publishes `/var/lib/personal-codex-router/collector-status.json`, mode `0640`, with `quarantined_total`, `failed_spools`, `last_success_at`, and `last_run_at`. It writes a temporary file, syncs it, atomically renames it, and syncs the containing directory. Failed runs retain the previous success timestamp and publish committed aggregate counts. The ops service reads only this file; its strict read-only sandbox never opens the WAL database or spool payloads. Failed files warn until removed and a subsequent collection publishes the new count; a quarantine increase warns until a subsequent probe observes no increase. The first quarantine count establishes a baseline. A missing, unreadable, or invalid status file reports unknown counts and an explicit health diagnostic; unit/timer checks continue.

`overview.health.usage_collection` and `/api/health` expose this component, including status, issues, last success, and aggregate counts. `/api/health` retains HTTP 200 for an accessible dashboard, but its `ok` field is false unless usage collection is recently observed and healthy. Collector problems remain available through these health APIs and Linux desktop notifications; the compact health strip keeps its existing layout.

The dashboard no longer shows Codex, Claude or shared notice tiles, including usage-collection notices and notification-storage warnings. Account cards retain sign-in actions, quota, resets, renewal dates, plan badges and routing switches.

Notifications are generated on Linux even while the browser is closed and continue through the existing **Linux desktop notification service** when available. The server supplies their compact wording through `overview.notifications.items`, which `scripts/router-ops.py` consumes. Renewal notices say “Renews tomorrow”, “Renews in 2 days”, or “Renews 20 Oct”, adding “· date unconfirmed” for estimates. Relative renewal days use America/Santiago calendar dates, including across daylight-saving changes. Notices identify accounts by email. They do not send email, chat, or third-party push messages. Linux desktop delivery is not a guarantee of phone notification delivery; no phone push provider is configured.

## Triggers and noise control

- **Sign-in required:** the account's provider quota request returns HTTP 401, or gateway metadata explicitly reports an invalidated/reused/expired refresh token or `invalid_grant`. Generic 403 responses and network errors are shown as unknown instead of falsely telling the user to sign in. One notice is kept per episode; a fresh confirmed authentication recovery clears the episode even if routing remains unavailable or allowance is not reported. Outages and restarts do not create new episodes.
- **Weekly exhaustion:** with the single configured Codex account, fresh exhaustion produces the critical “Weekly limit reached · no account can serve” notice, with reset countdown and eligible redemption metadata. Retired account notices and old pool episodes are closed. In a multi-account setup, fresh successful quota observations generate “Weekly limit reached · using the other account” when traffic can use the other account. Without a confirmed fallback, the critical notice says “Weekly limit reached · no account can serve”; when both accounts are exhausted, it says “Weekly limits reached · Codex requests fail”. Critical notices append a countdown to the earliest reported future reset, when available. Account cards and the notice's structured API fields retain reset dates and credit balances. Exhaustion never triggers automatic credit redemption. When an exhausted account has available eligible credits, its API notice includes redemption metadata; the both-exhausted metadata chooses the eligible account whose credit expires first. Expired credits and unavailable accounts are excluded. Use the account card to redeem a reset manually. Existing expiry-based reset automation remains a separate policy.
- **Exhaustion episodes:** notices and legacy dismissal flags survive polling, outages, and restarts. A both-exhausted notice supersedes a single-account notice without resetting its dismissal. Fresh positive weekly allowance clears the affected account's episode and clears a both-exhausted episode, restoring any unresolved single-account notice even if its quota refresh failed; a later exhaustion creates a new notice even if the previous one was dismissed. Unknown/stale quota observations retain episodes but remove redemption actions until eligibility can be confirmed again.
- **Failed expiring reset:** one notice per account/credit when an automatic reset cannot be confirmed or no reset is applied. Retries retain the same durable redemption ID and do not create additional notices. Success resolves the notice. Expiry changes its wording to past tense, without claiming it succeeded. Legacy dismissal flags persist across retries and restarts. A failed notice ages out after seven days. The provider still decides applicability; no credit is consumed for notification testing.
- **Renewal:** one upcoming reminder in the final seven calendar days, and one review reminder in the final two, using America/Santiago dates. Confirmed billing dates and expected/unconfirmed entitlement dates use different wording. Dates are never rolled forward by assumed monthly recurrence. Past dates generate no invented renewal reminders; the existing account card shows “Check date”.
- **Usage collection:** one notice per unhealthy episode, labelled “Usage collection”. Repeated failed runs, changed failure reasons, dashboard/probe restarts, and legacy dismissal flags reuse the same durable notice ID. Missing or stale observations retain an existing episode; confirmed healthy collection clears it. A later failure starts a new episode with a new ID. No initial notice is invented before usage health has been observed.

Notification state lives at `/var/lib/personal-codex-router/notifications.json`, mode `0600`, and is included in settings backups. Desktop delivery history lives privately in `/var/lib/personal-codex-router-ops/desktop-delivery.json`. Successful desktop submissions are deduplicated independently of browser sessions. A crash exactly between desktop submission and saving its delivery record can replay one popup; the durable notification store remains authoritative. A closed/unavailable desktop does not prevent notifications from being saved. The store still honors dismissal flags written by older dashboards, but the dashboard no longer offers dismissal or a dismissal endpoint.

Exhaustion items in `overview.notifications.items` retain `id`, `email`, `message`, and `created_at`. They add `kind` (`weekly_exhausted` or `pool_exhausted`), `urgency` (`normal` or `critical`), and `accounts`: an array of `{"account_id":"<id>","label":"<account email>","weekly_resets_at":<epoch seconds or null>,"reset_credits_available":<integer or null>}` for the exhausted accounts. When redemption is eligible they also include `"action":{"type":"redeem_reset","account_id":"<id>","label":"<account email>"}`; otherwise `action` is omitted. These API fields remain available; manual redemption uses the account card's reset controls and the existing confirmed `/api/resets/consume` request. Desktop delivery sends `org.freedesktop.Notifications.Notify` through `gdbus`, mapping notice urgency to the urgency hint (critical notices stay until closed) and defaulting older notices to `normal`. It doesn't use `notify-send`: Ubuntu's AppArmor profile for it denies the session bus from the ops unit's private mount namespace.

The phone proxy permits fixed static assets, overview/health reads, and POSTs to `/api/refresh`, `/api/routing`, `/api/resets/policy`, and `/api/resets/consume`. It strips the obsolete read-only header and retains device, Host, Origin, and cross-site restrictions. No management key, OAuth token, provider error body, or arbitrary gateway route is forwarded to the browser.

The new units are `personal-codex-router-ops.timer` and `.service`. Their summary files are root-owned and readable by the dashboard group. The dashboard cannot write them. The daemon socket resolves under `/tmp/codex-daemon-1000`, so this probe deliberately shares the host temporary directory while keeping the filesystem read-only except for its private status directory.

To stop local desktop delivery and the Codex probe without changing account routing or reset automation:

```sh
sudo systemctl disable --now personal-codex-router-ops.timer
```

The Codex indicator will become stale and desktop delivery will stop; account cards still update with the dashboard's existing background polling.
