# Account lifecycle backend

Implemented against CLIProxyAPI v8.0.47 source and isolated fake management servers. No live OAuth session, service deployment, or live account deletion was performed.

## API for the dashboard

Every request retains the existing host, CSRF (`X-Router-Request: 1`), same-origin and no-store protections. New endpoint failures return `{error, message}` with an appropriate HTTP status. Existing Codex re-authentication and provider-specific routing request shapes remain supported.

| Request | Body / query | Success |
| --- | --- | --- |
| `GET /api/overview` | Existing query | Adds top-level `gateway_compat: {version, tested, supported}` and `add_providers: [{id, name, login, callback_example?}]`; generic provider accounts have `routing_enabled`; every provider account has `confirm_text` for disconnect and `models: {count, items: [{id, display_name?}]} | null` |
| `POST /api/accounts/add/start` | `{provider}` | `{session, provider, flow, url, auto_callback, user_code?, expires_at}` |
| `GET /api/accounts/add/status` | `?session=...` | `{state, account?: {key, provider, label, replaced}, message?}` |
| `POST /api/accounts/add/callback` | `{session, redirect_url}` | `{accepted: true}` |
| `POST /api/accounts/add/cancel` | `{session}` | `{cancelled: true}` or `{cancelled: false, state}` |
| `POST /api/accounts/disconnect` | `{key, auth_index, confirmed: true, confirm_text}` | `{disconnected: true, key, last_ready}` |
| `POST /api/accounts/routing` | `{key, auth_index, enabled}` | `{key, enabled}` for providers other than Codex/Claude |

The catalog includes Claude, Codex, Antigravity, Grok (`xai`), Kimi (`kimi` and `kimi-ai`), and Meta whenever the gateway's `X-CPA-VERSION` is supported: a strict numeric `major.minor.patch` in major 8, at least `8.0.47`. `dev`, malformed versions, older versions and major 9 or later are unsupported. Only the explicit tested set (`8.0.47`) sets `gateway_compat.tested: true`; a newer supported version is usable but untested. Start independently checks a fresh version before invoking any v8 OAuth operation. Devin is omitted. The catalog is empty before the first successful normal gateway/config refresh or when that refresh cannot establish a supported version. Unknown version is represented as `null` with `tested: false, supported: false`.

Status values are `waiting`, `finishing`, `ok`, `error`, `expired`, and `cancelled`. `waiting` and `finishing` are active and keep the single-session slot busy. The UI must keep polling `finishing`, show the returned message, and retain the session instead of allowing another start. A transient management read failure preserves the active state with a fixed, sanitized message so polling can retry. Gateway-declared failures return `error` without exposing upstream details. Unknown/restarted/pruned dashboard sessions return HTTP 409 `session_changed`. HTTP 409 `busy` means a different pending add must finish or be cancelled first. Cancellation is idempotent for a retained session and never undoes a completed sign-in. Only an explicit gateway `cancelled: true` makes cancellation terminal. A refused cancellation (the gateway may be saving credentials) returns `{cancelled: false, state: "finishing"}`. Completed sessions return `{cancelled: false, state: "ok"}` (or `error` for a failed session); the UI must poll status to collect the final account result. Transport failures preserve the busy slot, even when cancel returns HTTP 503.

`expires_at` is a UTC ISO timestamp. Sessions default to five minutes when the gateway omits an expiry; a positive gateway `expires_in` is capped at fifteen minutes. Terminal sessions remain available for ten minutes after terminal confirmation. Active sessions are never pruned by local expiry. Sessions are process-local and disappear on dashboard restart. Only one pending add is allowed across all providers, under the shared lifecycle lock. There are no added background polling threads: status requests poll the gateway's state-bound status endpoint. Expiry requests gateway cancellation; it becomes terminal `expired` only after confirmed cancellation. If cancellation is refused or unavailable, the session stays `finishing` and busy until gateway status reports `ok` or `error` (or a later cleanup succeeds). Unknown/malformed status responses also preserve the active slot.

The browser URL must have HTTPS and the provider's exact expected origin: `claude.ai`, `auth.openai.com`, `accounts.google.com`, `accounts.x.ai`, `auth.kimi.com`, `auth.kimi.ai`, or `auth.meta.com`. Browser authorization URLs must contain the same state returned by management. The opaque dashboard session handle binds the provider and gateway state server-side; callers cannot select either when submitting a callback.

Callbacks accept HTTP or HTTPS, `localhost` or `127.0.0.1`, and only these exact port/path pairs: Claude `54545/callback`, Codex `1455/auth/callback`, Antigravity `51121/oauth-callback`. A single nonempty code and exactly matching state are required. Wrong provider flow, duplicate code/state, credentials in the URL, fragments, control characters, backslashes and OAuth error callbacks are rejected. The dashboard never fetches the callback URL; it forwards `{provider, redirect_url}` to management. Browser OAuth starts with `is_webui=true` for local/SSH requests; Tailscale requests and device flows use `false`. Tailscale starts return `auto_callback: false` and do not open a callback listener. The start result includes `auto_callback: true` only when a browser callback forwarder was started. The desktop browser can complete sign-in without pasting. The paste endpoint remains available in either mode, including when the browser is on another device. On HTTP 500 `failed to start callback server` (the upstream public error for a listener bind failure), start retries once with `is_webui=false` and returns `auto_callback: false`. Other failures do not trigger a retry. If an error includes a valid session state, cancellation or terminal status must be confirmed before retry; refused/unavailable cleanup retains the single busy slot for reconciliation.

Upstream limitation: stock v8.0.47 registers its session before binding, returns no state in the bind-error response, and exposes cancellation only by state (no session-list endpoint). That inaccessible session cannot be explicitly cancelled through management; it has no callback waiter and expires from the upstream store after its thirty-minute TTL. The fallback can still create a usable paste session. Fully explicit cleanup on this path requires an upstream change to return state or cancel before responding. No live OAuth request was used to verify this behavior.

After success, inventory is read again. One changed/new file for the selected provider supplies `account`; a previously existing filename produces `replaced: true`. Identification compares identity/file timestamps and claims, excluding changing usage counters. If attribution is ambiguous or no change is observable, `ok` omits `account` and supplies a refresh message rather than identifying an arbitrary account. Success invalidates the existing refresh throttle and starts the normal overview refresh. The UI should follow its existing overview refresh cycle while `gateway.refreshing` is true.

## Disconnect and routing

Disconnect and existing sign-in-again start/cancel are available through Tailscale. The proxy allowlists these routes with the existing account-mutation timeout (45-second backend deadline plus a 5-second proxy margin). Explicit read-only requests remain read-only: disconnect returns HTTP 403 `read_only` before inventory or filesystem access. Existing host, CSRF and origin checks still apply.

Every disconnect requires `confirmed: true` and `confirm_text` matching the fresh account email, or its provider display name (for example, `Grok`) when it has no email. This shared server-defined value is exposed as `confirm_text` on each overview account. API-key accounts use their compatible-provider custom name or the last four key characters. Matching trims both strings and is case-insensitive. Missing, non-string, empty or mismatched confirmation returns HTTP 400 `{error: "confirm_mismatch", message}` before backup or deletion. `confirmed: false` still returns `confirmation_required`. Identity is revalidated under the existing lifecycle/controller locks before mutation.

Disconnect and routing take the lifecycle lock and the provider's existing controller file lock. They resolve a fresh inventory by filename and `auth_index`, reject duplicate/changed identities with HTTP 409 `account_changed`, and require management readback. Generic routing PATCHes `{name, auth_index, disabled: !enabled}`. Codex/Claude continue to use their existing routing endpoints and safety checks.

Disconnect supports ordinary file credentials for every provider on supported gateways (major 8, at least `8.0.47`). Unsupported gateway versions and unsafe file shapes return HTTP 409 `disconnect_unsafe`. Codex SIWC credentials remain refused. Upstream `sdk/auth/filestore.go:101-127` uses the cross-process per-file lock only for Codex; other providers have only an in-process mutex, so acquiring a dashboard sidecar lock would not exclude their writers.

Codex disconnect validates the configured auth-directory path and refuses symlinks, virtual/external files, unsafe filenames and SIWC. Disk device/inode/size/timestamps bracket the final fresh inventory identity read: the second disk check occurs under `credential_replace.credential_lock`, which also covers the backup and local unlink. A bounded backup is created exclusively with mode `0600`, flushed and fsynced, and the backup directory is fsynced before removal. The auth directory is fsynced after unlink.

Management calls never run under this file lock: gateway saves can hold the file-store mutex while waiting for it, making management calls unsafe to compose with it. Codex disconnect unlinks locally under the lock, releases it, and allows the watcher to remove runtime routing.

Other providers resolve fresh inventory by filename and `auth_index` and require an ordinary file inside the configured auth directory, rejecting symlinks, virtual/runtime-only files and external paths. Device/inode/size/mtime (and ctime) checks surround a bounded, exclusive mode `0600` backup; the backup file and directory are fsynced before removal. If the file changes during backup or the final stat check, the operation repeats the fresh inventory and backup once, then returns HTTP 409 `account_changed` if it changes again. A stable backup is followed by management `DELETE /v0/management/auth-files?name=...`, which removes the file and runtime auth.

Residual risk: a gateway token refresh landing between the final stat check and DELETE can make a non-Codex backup's tokens a few seconds stale. Restoring that backup may then require a new sign-in. The account identity cannot change in this window because gateway filenames include the account identity.

Both removal paths use the same readback. Up to ten bounded attempts (100 ms between attempts, within the existing request deadline) require that the file is absent, no inventory row matches filename/auth_index/path, and `/auth-files/models?name=...` returns an empty model registry. Lingering disk files, runtime-only inventory or registered models return HTTP 503 `unconfirmed`; success is never inferred from disk absence alone. Backups remain available after failed or unconfirmed removal and are never returned through the API. No credential content is logged.

The approved backup location is `/var/lib/personal-codex-router/disconnected`, owned by `cliproxyapi`, mode `0700`; files are readable only by the service and root. This is the user-approved adjustment from the original root-only-directory wording, which a non-root dashboard cannot write. `install-operations.py` creates that directory on full, account-access and Claude-watch installs. It sits beneath the dashboard service's existing `ReadWritePaths=/var/lib/personal-codex-router`, so no service-unit change is needed. A backend-only `--t3-usage-only` deployment ships the import dependencies but intentionally does not provision this directory; disconnect fails closed until it exists with the correct permissions.

`last_ready` reports whether any other account of that provider is ready. Codex uses its existing live quota classification, Claude uses its existing watched-usage eligibility, and other providers use active/enabled/available gateway inventory. If readiness cannot be established, the result is conservative (`true`). No routing preference is rewritten on removal: PR1's existing retired-preference behavior remains in effect. The UI should use filename `key` and `auth_index` from the latest provider account row, warn before confirming the final ready account, require typed confirmation and hide disconnect when the overview is explicitly read-only. Tailscale transport alone does not restrict disconnect or sign-in-again.

## Models per account

The existing background gateway poll queues `GET /v0/management/auth-files/models?name=<filename>` on its existing four-worker pool for every inventory file. The per-filename cache lasts ten minutes; failures are also throttled for ten minutes and preserve the last successful list. Until a successful read, `providers[].accounts[].models` is `null`. A successful empty registry is `{count: 0, items: []}`. Only `id` and optional nonempty string `display_name` are projected, sorted by id; `type`, `owned_by` and other registry fields are dropped. Overview and snapshot requests only copy cached data and never fetch model registries. No extra polling threads or separate executors are added.

## Callback listener exposure

Read-only `sudo -n nft list ruleset` on the Linux desktop on 2026-10-30 found that LAN input is accepted and the host guard does not restrict TCP 54545, 1455 or 51121 on LAN interfaces. Therefore the gateway's temporary `0.0.0.0` callback forwarders are potentially reachable from LAN while active. New Tailscale connections to these ports hit the host guard's final drop: they are not allowlisted. This is firewall-rule evidence, not a remote connection probe; Tailscale ACLs and upstream network controls were not tested. No firewall changes were made.

## Source checks for the review fixes

Provider origins were checked against the upstream `v8.0.47` tag (release commit `90c447d3`). Browser URLs come from `internal/auth/claude/anthropic_auth.go:24`, `codex/openai_auth.go:25`, and `antigravity/constants.go:23`. xAI's issuer is `auth.x.ai`, but `internal/auth/xai/xai_auth_test.go:52-53` specifies `https://accounts.x.ai/oauth2/device` and its complete user-code URL. Only `accounts.x.ai` is allowed for the xAI verification URL; arbitrary x.ai subdomains remain rejected. Meta's `internal/auth/meta/meta_auth_test.go:29-30` uses `https://auth.meta.com/device`. Kimi's `internal/auth/kimi/kimi.go:36-38` and `kimi_test.go:218-233` confirm the separate `auth.kimi.com` / `auth.kimi.ai` device/token hosts; the response's verification URL is provider-supplied, and upstream has no literal verification-URI fixture for Kimi, so the existing exact hosts remain the conservative allowlist. No live device-code request was made.

Cancellation follows `internal/api/handlers/management/oauth_sessions.go:350-378`: cancellation returns false while committing, after completion, and for missing/failed sessions. Status distinguishes these cases; committing sessions are retained through upstream expiry (`oauth_sessions.go:76-78`). Regression fixtures use independent provider URLs, cancellation-false and unavailable-cleanup responses, a competing flock at backup/unlink, a successor-file replacement, and lingering runtime models.
